# 자산 관리 재정의 (핵심)

이 문서는 이번 재설계의 심장이다. 기존 자산 관리의 불만을 해소하기 위해
**무엇을 어떻게 단순화하는지**를 정의한다.

## 1. 멘탈 모델

> **계좌는 두 가지를 담는다: 현금 잔고 + 보유 종목들.
> "지금 상태가 어떤지" 사진 한 장을 찍는다 — 기본은 월말, 필요하면 주 단위 등 더 자주.**

```
구성원(Member)
  └─ 계좌(Account, 기관 소속)
       ├─ 현금 잔고  ──► CashSnapshot   (snapshotDate, cashBalanceKRW)
       └─ 보유 종목  ──► HoldingSnapshot (snapshotDate, quantity, avgCostKRW, currentPriceKRW)
```

> 스냅샷 키는 `snapshotDate`(일자)다. 기본 사용 흐름은 월말 마감이지만, 같은 스키마로
> 임의 시점(주 단위 등) 스냅샷도 찍을 수 있다.

- **현금**은 "어디에 얼마"만 의미가 있다. 수익률 개념이 없다.
  은행↔증권 이동은 기록하지 않는다 — 다음 달 잔고만 다르게 찍으면 끝이다.
- **종목**은 "얼마 넣었나(원금)"와 "지금 얼마인가(평가액)"가 핵심이다.
  여기서 수익·수익률이 나온다.

이 분리가 기존 불만("현금과 종목이 뒤섞여 투자 현황을 못 본다")의 직접적 해소책이다.

## 2. 두 가지 입력 유형

종목은 성격에 따라 입력 방식이 다르다. 화면은 자동으로 유형을 판별해 필요한 칸만 보여준다.

| 유형 | 대상 | 입력 칸 | 원금/평가액 |
|------|------|---------|-------------|
| **value형** | 현금형 종목(예금·청약·MMF·RP 등), 계좌 현금 잔고 | 평가액 한 값 | 원금 = 평가액 (수익 0) |
| **quantity형** | 주식·ETF·채권·금·코인 등 | 수량 · 평균단가 · 현재가 | 원금 = 수량×평균단가, 평가액 = 수량×현재가 |

> value형은 내부적으로 `quantity=1, avgCostKRW=currentPriceKRW=평가액`으로 저장해
> quantity형과 동일한 스키마(`HoldingSnapshot`)를 쓴다. **입력 UX만 분기**하고 데이터 구조는 하나다.

## 3. 스냅샷 입력 워크플로우

```
1. 기준일 선택 (기본: 이번 달 월말. 필요 시 주 단위 등 임의 일자)
2. 시스템이 직전 스냅샷을 자동 복사해 폼을 채운다.
   - 계좌별 현금 잔고
   - 종목별 수량 · 평균단가 · 현재가
3. 사용자는 바뀐 값만 수정한다.
   - 보통 현재가만 바뀐다.
   - 매수/매도가 있었다면 해당 종목의 수량·평균단가를 직접 고친다.
   - 새 종목/계좌면 추가, 정리했으면 0 또는 제거.
4. 저장 → 해당 기준일 스냅샷 확정.
```

기본 사용 흐름은 월말 마감이며, 같은 폼으로 임의 시점(주 단위) 스냅샷도 찍을 수 있다.
기존의 복잡성(localStorage 임시저장, 그룹 전환 상태 유지, 부분 저장 누락 경고)은
**직전 스냅샷 복사 기반**으로 구조적으로 사라진다: 복사된 폼은 항상 완전하므로 누락이 발생하지 않는다.

### 평균단가 갱신 규칙

평균단가(`avgCostKRW`)는 매매가 있을 때만 바뀐다. 앱은 매매를 추적하지 않으므로,
사용자가 "현재 상태"로서 직접 입력한다.

- 추가 매수 시: 사용자가 새 수량과 새 평균단가를 직접 계산해 입력한다.
- 매도 시: 남은 수량으로 줄이고 평균단가는 보통 유지한다.
- 시드 초기값: 평균단가 = 현재가 (수익 0에서 출발, 이후 보정).

## 4. 정합성 규칙

| 값 | 산출식 | 저장 여부 |
|----|--------|-----------|
| 원금 | `quantity × avgCostKRW` | ✗ 파생 (저장 안 함) |
| 평가액 | `quantity × currentPriceKRW` | ✗ 파생 |
| 수익 | `평가액 − 원금` | ✗ 파생 |
| 수익률 | `수익 / 원금` (원금 0이면 표시 안 함) | ✗ 파생 |

저장하는 것은 오직 **입력값**(quantity, avgCostKRW, currentPriceKRW, cashBalanceKRW, exchangeRate)뿐이다.
모든 지표는 조회 시 계산한다 → 저장값 간 불일치가 원천적으로 불가능.

## 5. 외화 처리

외화 종목은 입력 시 **통화·환율**을 받아 **원화 환산값을 저장**한다.

- `avgCostKRW`, `currentPriceKRW`는 항상 원화 기준으로 저장.
- `exchangeRate`는 해당 월 적용 환율을 참고용으로 함께 저장(원화 종목은 null).
- 외부 환율 API는 쓰지 않는다 — 사용자가 입력한다.

## ADR: 거래 기록 테이블을 두지 않는다

### 맥락
기존 설계는 `HoldingTransaction`(매수/매도 기록)으로부터 보유량·평균단가를 자동 재계산하고,
별도로 `HoldingValueSnapshot`(수동 입력)을 두었다. 두 체계가 분리되어 어긋났고,
거래 수정 기능 부재·정합성 보증 곤란 등의 문제가 누적됐다.

### 결정
**스냅샷을 유일한 진실원천(SSOT)으로 삼는다.** 사용자는 매매가 아니라 "현재 보유 상태"를
직접 입력하며, 모든 지표는 스냅샷에서 파생한다.

### 개정 (2026-06-04): 거래 기록은 비권위로 유지
거래 기록 테이블/화면(`HoldingTransaction`, `/asset/transactions`)을 **삭제하지 않고
비권위(non-authoritative) 보조로 유지**한다. 향후 재도입 가능성에 대비한 결정이다.

- 스냅샷이 항상 진실원천이다. 거래 입력은 `Holding` 현재 상태나 스냅샷 값을 **자동으로 덮어쓰지 않는다**.
  (현재 코드는 거래가 `Holding.quantity/averageCostKRW`를 재계산하므로, 이 연결을 끊거나
  스냅샷 우선으로 재정의하는 것이 구현 전제다.)
- 거래 화면은 참고/보조 입력 용도로만 노출한다. 재도입 시 "거래 → 스냅샷 반영" 방향을 검토한다.

### 트레이드오프
- **포기**: 표준 흐름에서의 자동 실현손익 추적·자동 평균단가 계산.
- **획득**: 단일 진실원천, 정합성 보증, 입력/구현 단순성.
- **유의**: 거래 화면을 유지하므로 "두 체계 어긋남" 위험이 재발하지 않도록 비권위 격리가 필수다.

### 근거
정기적으로 현황을 기록하는 가족 자산 관리에서는 **거래 단위 정확도보다 시점별 포트폴리오 현황**이
실질적 가치다. 거래 추적은 가장 큰 복잡성의 근원이었고, 사용자의 핵심 니즈(현금/투자 분리와
수익 인사이트)는 스냅샷만으로 충족된다.
