# 자산 관리 재정의 (핵심)

이 문서는 이번 재설계의 심장이다. 기존 자산 관리의 불만을 해소하기 위해
**무엇을 어떻게 단순화하는지**를 정의한다.

## 1. 멘탈 모델

> **계좌는 두 가지를 담는다: 현금 잔고 + 보유 종목들.
> "지금 상태가 어떤지" 사진 한 장을 찍는다 — 기본은 월말, 필요하면 주 단위 등 더 자주.**

```
구성원(Member)
  └─ 계좌(Account, 기관 소속)
       ├─ 현금 잔고  ──► CashSnapshot   (snapshotDate, cashBalanceKRW)
       └─ 보유 종목  ──► HoldingSnapshot (snapshotDate, quantity, avgCostKRW, currentPriceKRW)
```

> 스냅샷 키는 `snapshotDate`(일자)다. 기본 사용 흐름은 월말 마감이지만, 같은 스키마로
> 임의 시점(주 단위 등) 스냅샷도 찍을 수 있다.

- **현금**은 "어디에 얼마"만 의미가 있다. 수익률 개념이 없다.
  은행↔증권 이동은 기록하지 않는다 — 다음 달 잔고만 다르게 찍으면 끝이다.
- **종목**은 "얼마 넣었나(원금)"와 "지금 얼마인가(평가액)"가 핵심이다.
  여기서 수익·수익률이 나온다.

이 분리가 기존 불만("현금과 종목이 뒤섞여 투자 현황을 못 본다")의 직접적 해소책이다.

## 2. 두 가지 입력 유형

종목은 성격에 따라 입력 방식이 다르다. 화면은 자동으로 유형을 판별해 필요한 칸만 보여준다.

| 유형 | 대상 | 입력 칸 | 원금/평가액 |
|------|------|---------|-------------|
| **value형** | 현금형 종목(예금·청약·MMF·RP 등), 계좌 현금 잔고 | 평가액 한 값 | 원금 = 평가액 (수익 0) |
| **quantity형** | 주식·ETF·채권·금·코인 등 | 수량 · 평균단가 · 현재가 | 원금 = 수량×평균단가, 평가액 = 수량×현재가 |

> value형은 내부적으로 `quantity=1, avgCostKRW=currentPriceKRW=평가액`으로 저장해
> quantity형과 동일한 스키마(`HoldingSnapshot`)를 쓴다. **입력 UX만 분기**하고 데이터 구조는 하나다.

## 3. 스냅샷 입력 워크플로우

```
1. 기준일 선택 (기본: 이번 달 월말. 필요 시 주 단위 등 임의 일자)
2. 시스템이 직전 스냅샷을 자동 복사해 폼을 채운다.
   - 계좌별 현금 잔고
   - 종목별 수량 · 평균단가 · 현재가
3. 사용자는 바뀐 값만 수정한다.
   - 보통 현재가만 바뀐다.
   - 매수/매도가 있었다면 수량을 고친다(평균단가는 수량 변화로 자동 파생되며, 필요 시 직접 보정).
   - 새 종목/계좌면 추가, 정리했으면 0 또는 제거.
4. 저장 → 해당 기준일 스냅샷 확정.
```

기본 사용 흐름은 월말 마감이며, 같은 폼으로 임의 시점(주 단위) 스냅샷도 찍을 수 있다.
기존의 복잡성(localStorage 임시저장, 그룹 전환 상태 유지, 부분 저장 누락 경고)은
**직전 스냅샷 복사 기반**으로 구조적으로 사라진다: 복사된 폼은 항상 완전하므로 누락이 발생하지 않는다.

### 입력 화면 구조: 소유자 ▸ 기관 스텝

사용자의 실제 입력 흐름은 **소유자별로 점검 → 각 기관 앱을 하나씩 열어 그 기관의
현금성·종목을 한 번에 갱신**하는 것이다. 입력 화면도 이 흐름에 맞춰 **소유자 ▸ 기관 묶음 스텝**
2단 위계로 정돈하고, **한 번에 한 묶음만 펼쳐** 파악 부담을 줄인다.

```
소유자(Member)
  ├─ "예금" 스텝        ── 은행류 기관(institution.type='bank')의 현금성 자산을 한 묶음에 나열
  ├─ {증권사 A} 스텝    ── 그 기관 계좌의 예수금(CMA 등 value형) + 종목(quantity형)
  ├─ {증권사 B} 스텝
  └─ ...
```

- **스텝 분기 기준은 자산의 value/quantity가 아니라 소속 기관의 type다.**
  - `institution.type === 'bank'` → 소유자별 **"예금" 한 스텝**으로 묶어 기관별로 나열.
  - `institution.type === 'brokerage'` → **기관마다 한 스텝**. 그 안에 예수금(value형)과 종목(quantity형)이 함께 들어간다.
- **예수금은 별도 현금 모델이 아니라 해당 기관의 CMA 통장 등 value형 holding으로 기재**한다.
  사용자가 각 기관 앱에서 예수금과 종목을 한 번에 조회하므로, 입력 화면도 기관 단위로 완결된다.
- 각 행에는 **`기관명 · 계좌명`** 맥락을 노출해 동명 자산(예: 여러 은행의 "원화예금")을 구별한다.
- 현금성(value형) 행과 종목(quantity형) 행은 아이콘·헤더로 시각 구분한다.
- 진행률은 **소유자별 완료 묶음 수**(예: "남편 3/5 묶음 완료")로 표시한다. 묶음 완료 =
  그 묶음의 모든 행에 이번 달 값이 채워짐.

##### 탭·펼침·수정 표시

- **소유자 선택은 탭**으로 둔다. 상단 소유자 탭에서 한 명을 고르면 그 소유자의 기관 묶음만 보이고,
  나머지 소유자는 탭 형태로 존재한다(한 화면에 모든 소유자를 쌓지 않는다).
- 기관 묶음은 기본 접힘이며, 활성 기관 표 헤더의 **"모두 펼치기/접기"** 로 그 기관 한 곳의
  세부정보(계좌 그룹 + 수량형 종목의 상세 입력)를 한꺼번에 토글한다. 다른 기관은 영향받지 않는다.
- **수정 표시는 "이번 세션 편집" 기준**이다. 패널을 연 시점의 서버 스냅샷 값과 비교해
  사용자가 이번에 바꾼(또는 새로 추가한) 항목만 수정으로 본다. 전월 대비 변화(증가/감소/유지/신규)는
  상태 배지가 따로 담당한다.
  - 기관 칩·표 헤더·계좌 그룹·소유자 탭: 해당 범위에 수정 행이 있으면 **주황 동그라미**. 표시 우선순위는
    수정됨 > 완료(초록 체크) > 미입력 카운트 — 자동 채움으로 모든 기관이 "완료"로 보여 수정처럼 오인되던 혼동을 없앤다.
  - 수정된 세부 자산 행: **행 배경을 accent 틴트**(디자인의 `.changed` 관례)로 표시한다.
- 다음 묶음 이동 버튼은 **"다음: {기관명}"** 으로 간결화한다(다음 묶음이 다른 소유자면 탭도 함께 전환).

##### 행 입력 칸 구성

각 행의 입력 칸은 "각 기관 앱에서 보는 값을 그대로 옮겨 적는" 흐름에 맞춘다.

- **value형(예금·예수금 등)**: "이번 달" 칸에 평가액 한 값만 입력한다.
- **quantity형(주식 등)**: "이번 달" 칸은 **수량×현재가로 자동 계산되는 평가액을 읽기 전용으로 표시**한다
  (직접 수정하지 않는다). 실제 입력은 행을 펼친 세부 칸에서 한다.
  - **원화 종목**: 수량 · 현재가 · 평균단가 3칸만 노출(환율·원통화 칸은 숨김).
  - **외화 종목**: 수량 · 현재가(원통화) · 환율 · 평균단가 4칸을 입력한다.
    **원화 현재가(현재가×환율 자동 계산)는 현재가 칸 밑 파생 캡션(`원화 … · 자동`)으로** 둔다(인풋 박스 아님).
- 금액 입력 칸(평가액·현재가·평균단가)은 **입력 중에도 천 단위 콤마**로 표시해 전월 표시와
  일관성을 맞춘다(수량·환율은 콤마 없이 입력).

###### 펼친 세부 = 편집 카드

펼친 영역은 표 위에 떠 있는 **하나의 편집 카드**다. 트레이(`bg-surface-soft`) 위에 카드(`bg-surface`)가
얹히고, 좌측 accent 엣지로 "편집 중"을 표시한다. 구성은 헤더 스트립 · 입력 한 줄 · 결과 패널 3부분.

- **헤더 스트립**: 좌측 `종목명 · 통화`, 우측 `전월값으로`/`정리` 액션(상태 배지와 분리). `전월값으로`는
  전월 스냅샷이 있을 때만, `정리`는 기존 종목에만 노출한다.
- **입력 한 줄**: `수량 · 현재가 · (환율) · 평균단가`를 균일 폭으로 한 줄 정렬한다. 각 칸은 라벨 ·
  우측정렬 인풋(`tabular-nums`) · 우측정렬 단일행 캡션(`전월 {값}` + 증감 칩)로 통일한다(넘침/줄바꿈 없음).
  - **현재가**는 보통 매달 바뀌는 주(主) 입력이라 라벨 옆 accent 점으로 강조한다.
  - **현재가** 증감: (현재−전월)/전월 = `▲ +9.5%` / `▼ -3.1%` / `· 유지`(외화는 원통화 기준).
  - **수량·평균단가**: 전월값과 `· 유지`(동일)/변동량을 중립색으로. **환율**: 전월값 참조만.
    전월값이 없는 신규 종목은 `신규`로 표시한다.
- **결과 패널**(우측, 구분선 + `bg-canvas`): 입력값에서 파생한 값을 **수익(히어로, ±·%) → 평가액 →
  원금** 순으로 보여 준다. 평가액 = 수량×현재가, 원금 = 수량×평균단가, 수익 = 평가액−원금(평균단가
  미입력 시 현재가로 간주). 평가액은 표의 '이번 달' 칸과 겹치므로 카드에서는 수익을 히어로로 둔다.

#### 자산/계좌/기관 추가

- **종목 추가(흔함)**: 각 계좌 그룹/단일계좌 스텝의 "종목 추가"에서 기존 종목 선택 또는 새 종목 생성. 계좌는 컨텍스트로 정해져 선택 불필요.
- **계좌·기관 추가(가끔)**: 패널 하단 "계좌·기관 추가"에서 소유자 → 기관(선택/＋신규) → 계좌(신규) → 첫 종목 순으로 진행. 기관/계좌/종목은 즉시 저장되고, 보유 행 평가액은 업로드 시 스냅샷으로 확정한다.
- 소유자(Member)는 생성하지 않고 기존 목록에서 선택만 한다.

### 평균단가 갱신 규칙

평균단가(`avgCostKRW`)는 매매가 있을 때만 바뀐다. 앱은 매매를 추적하지 않으므로,
**연속한 스냅샷의 수량 변화로 자동 파생**한다(상세 규칙·식은 `insights.md`의 "평균단가 자동 파생" 참조).

- 수량 증가(추가 매수 추정): 직전 원금과 이번 달 현재가로 **가중평균**해 자동 계산·prefill한다.
- 수량 감소/동일(매도·보유): 평균단가를 유지한다.
- 사용자는 필요 시 평균단가 칸을 직접 덮어쓸 수 있다 → 그 행은 보정값(`avgCostManual`)으로 전송되어 자동 파생보다 우선한다.
- 시드 초기값: 평균단가 = 현재가 (수익 0에서 출발, 이후 파생으로 누적).
- **적용**: 입력 화면은 수량/현재가 변경에 맞춰 평균단가 칸을 파생값으로 prefill하고, 저장 시 서버(`saveMonthlyInput`)가 직전 스냅샷을 다시 조회해 권위적으로 파생한다(보정값은 그대로 사용). 공유 규칙은 `src/lib/asset-cost.ts`의 `deriveAvgCostKRW`. value형(현금성) 종목은 파생 대상이 아니다.

## 4. 정합성 규칙

| 값 | 산출식 | 저장 여부 |
|----|--------|-----------|
| 원금 | `quantity × avgCostKRW` | ✗ 파생 (저장 안 함) |
| 평가액 | `quantity × currentPriceKRW` | ✗ 파생 |
| 수익 | `평가액 − 원금` | ✗ 파생 |
| 수익률 | `수익 / 원금` (원금 0이면 표시 안 함) | ✗ 파생 |

저장하는 것은 오직 **입력값**(quantity, avgCostKRW, currentPriceKRW, cashBalanceKRW, exchangeRate,
그리고 외화 종목의 원통화 입력값 priceOriginal·avgCostOriginal)뿐이다.
모든 지표는 조회 시 계산한다 → 저장값 간 불일치가 원천적으로 불가능.

## 5. 외화 처리

외화 종목은 입력 시 **통화·환율**을 받아 **원화 환산값을 함께 저장**한다.

- `avgCostKRW`, `currentPriceKRW`는 항상 원화 기준으로 저장(모든 집계·표시는 원화로 한다).
- `exchangeRate`는 해당 시점 적용 환율을 함께 저장(원화 종목은 null).
- 사용자가 외화로 입력한 **원통화 가격은 손실 없이 보존**한다: `priceOriginal`(원통화 현재가),
  `avgCostOriginal`(원통화 평균단가). 환율은 시점마다 다르고 현금형은 환율이 null이라
  원화값에서 역산하면 손실되므로, 원통화 입력값을 1급 데이터로 함께 저장한다. (원화 종목은 null)
- 외부 환율 API는 쓰지 않는다 — 사용자가 입력한다.

## ADR: 거래 기록 테이블을 두지 않는다

### 맥락
기존 설계는 `HoldingTransaction`(매수/매도 기록)으로부터 보유량·평균단가를 자동 재계산하고,
별도로 `HoldingValueSnapshot`(수동 입력)을 두었다. 두 체계가 분리되어 어긋났고,
거래 수정 기능 부재·정합성 보증 곤란 등의 문제가 누적됐다.

### 결정
**스냅샷을 유일한 진실원천(SSOT)으로 삼는다.** 사용자는 매매가 아니라 "현재 보유 상태"를
직접 입력하며, 모든 지표는 스냅샷에서 파생한다.

### 개정 (2026-06-04): 거래 기록은 비권위로 유지
거래 기록 테이블/화면(`HoldingTransaction`, `/asset/transactions`)을 **삭제하지 않고
비권위(non-authoritative) 보조로 유지**한다. 향후 재도입 가능성에 대비한 결정이다.

- 스냅샷이 항상 진실원천이다. 거래 입력은 `Holding` 현재 상태나 스냅샷 값을 **자동으로 덮어쓰지 않는다**.
  (현재 코드는 거래가 `Holding.quantity/averageCostKRW`를 재계산하므로, 이 연결을 끊거나
  스냅샷 우선으로 재정의하는 것이 구현 전제다.)
- 거래 화면은 참고/보조 입력 용도로만 노출한다. 재도입 시 "거래 → 스냅샷 반영" 방향을 검토한다.

### 트레이드오프
- **포기**: 거래 기록 기반의 _정확한_ 실현손익·평균단가 계산. (대신 스냅샷 수량 변화 기반 자동 파생·실현손익 추정으로 근사 — `insights.md` 참조.)
- **획득**: 단일 진실원천, 정합성 보증, 입력/구현 단순성.
- **유의**: 거래 화면을 유지하므로 "두 체계 어긋남" 위험이 재발하지 않도록 비권위 격리가 필수다.

### 근거
정기적으로 현황을 기록하는 가족 자산 관리에서는 **거래 단위 정확도보다 시점별 포트폴리오 현황**이
실질적 가치다. 거래 추적은 가장 큰 복잡성의 근원이었고, 사용자의 핵심 니즈(현금/투자 분리와
수익 인사이트)는 스냅샷만으로 충족된다.
